# AI Usage Report

In accordance with Section 1.11 and Phase 9 of the School Admission System PRD, this document transparently records the AI tools utilized, their purpose across development phases, and critical errors or false assumptions made by AI models that were caught, debugged, and corrected.

---

## 1. AI Tools Used

- **Claude 3.5 Sonnet / Antigravity Agent (Google DeepMind)**
  - Backend Minimal API design, PostgreSQL row-level locking architecture, integration test suites, React SPA state machines, and Docker containerization.

---

## 2. Where AI Was Used

1. **Architecture & Schema Planning**:
   - Designing the relational schema in EF Core with `snake_case` naming (`classes`, `holds`).
   - Defining the composite index `(class_id, status, expires_at)` to support high-speed concurrency queries.

2. **C# / ASP.NET Core Boilerplate**:
   - Scaffolding the 8 required REST endpoints across `ClassEndpoints.cs` and `HoldEndpoints.cs`.
   - Creating strongly typed DTO records (`CreateClassRequest`, `ClassResponse`, `HoldCreatedResponse`, etc.).
   - Configuring exception handling middleware (`ApiExceptionHandler`) to return clean `{ status, message }` JSON payloads without stack traces.

3. **Concurrency & Test Design**:
   - Formulating the 50-request parallel test (`Parallel_applications_never_exceed_total_seats`) using `Task.WhenAll` and `WebApplicationFactory`.
   - Constructing tests for idempotent confirmation, duplicate prevention, and expired hold reclaim.

4. **Frontend Architecture**:
   - Building the pure CSS design system matching the admission mockups without bulky UI component libraries.
   - Implementing custom hooks (`useCountdown.ts` and `useStudentId.ts`) with local storage persistence and dynamic polling.

## 3. Real AI Mistakes Caught & How They Were Fixed

During development, several AI-generated proposals were factually incorrect, violated PRD invariants, or caused runtime bugs. Below are the specific issues identified and resolved:

### Mistake 1: In-Memory Locking (`lock` / `SemaphoreSlim`)
- **What the AI proposed**: To avoid overselling seats, the AI initially suggested wrapping seat reservation checks inside a C# in-memory synchronization primitive (`SemaphoreSlim` or `lock (classLock)`).
- **Why it was wrong**: In-memory locks only protect a single process on a single server. In a distributed or multi-instance deployment (such as the PRD's Phase 10 bonus with `backend` and `backend2`), or if the application restarts, multiple instances will simultaneously read available seats and oversell.
- **How it was caught & fixed**: We rejected application-level locks and enforced database-level serializability using PostgreSQL exclusive row-locking:
  ```sql
  SELECT id FROM classes WHERE id = @classId FOR UPDATE;
  ```
  This guarantees that all concurrent backend processes queue at the database transaction layer.

---

### Mistake 2: PostgreSQL Table Identifier Case-Sensitivity
- **What the AI proposed**: In raw SQL queries for row locking, the AI generated:
  ```csharp
  await _db.Database.ExecuteSqlRawAsync(
      "SELECT \"Id\" FROM \"Classes\" WHERE \"Id\" = {0} FOR UPDATE", classId);
  ```
- **Why it was wrong**: EF Core PostgreSQL converts entity names to snake_case (`classes`, `holds`). Running queries with quoted PascalCase identifiers (`"Classes"`) caused runtime crashes:
  `Npgsql.PostgresException: 42P01: relation "Classes" does not exist`.
- **How it was caught & fixed**: We noticed the table naming schema generated by EF Core migrations and corrected the query to lowercase unquoted table and column names:
  ```csharp
  await _db.Database.ExecuteSqlRawAsync(
      "SELECT id FROM classes WHERE id = {0} FOR UPDATE", classId);
  ```

---

### Mistake 3: Unicode vs ASCII Student ID Validation (`char.IsDigit`)
- **What the AI proposed**: The AI wrote the 17-digit validation as:
  ```csharp
  if (studentId.Length != 17 || !studentId.All(char.IsDigit))
  ```
- **Why it was wrong**: In .NET, `char.IsDigit` returns `true` for Unicode digit categories, including full-width digits (e.g. `１２３`), Arabic-Indic digits, and subscript/superscript numbers. The PRD specifically requires strictly 17 ordinary decimal ASCII digits (`0-9`).
- **How it was caught & fixed**: We caught this during code review and replaced it with strict ASCII boundary checking:
  ```csharp
  if (studentId.Length != 17 || !studentId.All(c => c >= '0' && c <= '9'))
  ```

---

### Mistake 4: Docker Internal DNS vs Browser Client API URL
- **What the AI proposed**: The AI set the Vite frontend environment variable in Docker Compose to:
  ```yaml
  environment:
    - VITE_API_URL=http://backend:8080
  ```
- **Why it was wrong**: The React SPA executes inside the end-user's web browser, not inside the Docker network. The user's browser running on the host OS cannot resolve the internal Docker container name `backend`. Fetch requests resulted in `ERR_NAME_NOT_RESOLVED`.
- **How it was caught & fixed**: We configured Vite build arguments to bake the host-accessible URL:
  ```yaml
  args:
    VITE_API_URL: http://localhost:8080
  ```

---

### Mistake 5: Client-Side Clock Drift in Hold Countdown
- **What the AI proposed**: The AI calculated the remaining hold countdown using only local client time:
  ```ts
  const remainingSeconds = Math.max(0, Math.floor((new Date(expiresAt).getTime() - Date.now()) / 1000));
  ```
- **Why it was wrong**: If a guardian's device clock is fast or slow by even 2 minutes, the countdown displays incorrect time (e.g., showing 8 minutes remaining when only 6 remain, or showing expired when still valid).
- **How it was caught & fixed**: The backend returns `serverTime` in every hold response. The frontend measures clock skew on arrival:
  ```ts
  const serverOffset = new Date(serverTime).getTime() - Date.now();
  const adjustedNow = Date.now() + serverOffset;
  ```
  This anchors countdown display to the authoritative server clock regardless of client device drift.

---

### Mistake 6: Port Collision on Host Machine (5433 vs 5434)
- **What the AI proposed**: The AI followed the PRD default mapping of host port `5433:5432` for the PostgreSQL container.
- **Why it was wrong**: When verifying host port availability, ports `5432` and `5433` were already occupied by local Windows PostgreSQL background services (`postgresql-x64-13` and `postgresql-x64-18`). Attempting to bind port 5433 produced port conflict errors.
- **How it was caught & fixed**: We inspected running host connections with `Get-NetTCPConnection` and adjusted the Docker mapping to host port `5434:5432` across `docker-compose.yml`, `appsettings.json`, and backend connection strings.
